## 0.46：流入待機の上限と任意の検査プロセス

`gateway_admission_wait_ms` は 0〜2000 ミリ秒で、既定値 0 では満杯時に直ちに HTTP 503 を返します。正の値にすると、認証済み要求は最大 `gateway_max_inflight` 件まで待機できます。待機枠の超過や時間切れは、本文の読み取りや宛先への送信前に 503 で終了します。非冪等なツール操作も含め、ゲートウェイは自動再試行しません。

`inspector_replicas` は 1、2、4 に対応し、既定値は 1 です。2 または 4 では同じ Docker ホスト上で監督付き検査プロセスを起動します。Envoy は正常なプロセスに検査を分散し、検査不能時は fail-closed を維持します。これはホスト間 HA ではありません。実行中の要求はプロセス障害で失敗し、宛先の実行結果が不明な場合があります。クライアントで無条件に再試行しないでください。

`deploy/selfhost/deployment.yaml` で設定し、[セルフホスト手順](self-hosting.md)に従ってステージ・有効化した後、対象ホストで評価してください。マルチプロセス時のコンソールの遅延記録はゲートウェイプロセスのみで、検査プロセス内の時間は利用できません。設定だけで処理量や最初の内容までの遅延改善は保証されず、応答全体のバッファリングは継続します。

ゲートウェイは対応する応答全体を収集・検査してから内容を配信します。最初の内容までの遅延には収集と検査の両方が含まれます。完全な結果を待てる処理に適し、対話チャットは明確な遅延予算で評価する必要があります。

## 再現

Docker、Python 3.11以上、プロジェクトのconsole依存関係が必要です。一時スタックを構築し、実際の認証情報や有料APIを使わず、finallyでコンテナとボリュームを削除します。導入判断前にアイドル状態のホストで最低3回実行してください。

```bash
python -m pip install -e ".[console,compat,llm-compat]"
python -m examples.latency.benchmark --output /tmp/latency.json
```

## 解釈

コンソールは現在のプロセスの段階別直近256件を表示します。ゲートウェイ計測はクライアント配信前に終了します。Envoy往復は要求検査、上流収集、応答検査、通信を含みます。検査時間はキュー待機を含みます。失敗を含む独立した分布で、要求単位の対応がないため差を計算できず、再起動で消えます。サンプルなしは未測定でありゼロではありません。

## 0.45 要求単位の遅延と流入制限

コンソールは現在のプロセスで完了した直近64件のゲートウェイ要求タイムラインを表示します。各行には数値の時間、HTTP状態、完了状態だけを保持します。署名されたランダムIDは内部の結合にのみ使い、画面には表示しません。本文、パス、認証情報、エージェントIDは保存しません。初期認証と流入拒否はゲートウェイ結果に表示します。

検査ストリーム待機、ワーカーキュー、実行時間を別々に表示します。本文待機はメタデータ検査後からバッファされた本文が検査器に届くまでで、上流生成、通信、Envoyバッファを含みます。区間は重複や通信上の空白があるため合算できず、純粋なモデル遅延ではありません。再起動で消去されます。

`gateway_max_inflight`は整数4〜64で、既定値は32です。設定をステージして保守再起動で反映します。接続ウィザードは値を保持します。超過要求はHTTP 503です。低い値は拒否増加を許容して遅延を重視する業務向けです。合成比較の48では突発処理成功数が増えず、HTTP 500が発生しました。

単一の合成実行では一般的な最適値は決まりません。表を再現し、実機で代表的な応答、同時性、提供者制限、最初の内容と完了の遅延予算を評価してください。
