## 0.46: 제한된 진입 대기와 선택적 검사 프로세스

`gateway_admission_wait_ms`는 0~2000ms이며 기본값 0은 자리가 없을 때 즉시 HTTP 503을 반환합니다. 양수로 설정하면 인증된 요청이 최대 `gateway_max_inflight`건까지만 대기합니다. 대기 초과·시간 초과는 본문을 읽거나 대상 서비스를 호출하기 전에 503으로 끝납니다. 비멱등 도구 작업을 포함해 게이트웨이는 호출을 자동 재시도하지 않습니다.

`inspector_replicas`는 1·2·4를 허용하고 기본값은 1입니다. 2 또는 4는 같은 Docker 호스트에 감독되는 검사 프로세스를 띄웁니다. Envoy는 정상 검사기에 분산하고 검사가 불가능하면 차단합니다. 이는 서버 간 HA가 아닙니다. 작업 중 검사기가 사라지면 대상 서비스의 실행 여부가 불명확한 채 요청이 실패할 수 있으므로 클라이언트는 무조건 재시도하면 안 됩니다.

`deploy/selfhost/deployment.yaml`에서 설정하고 [셀프호스팅 절차](self-hosting.md)에 따라 스테이징·활성화한 뒤 대상 호스트에서 검증하세요. 다중 프로세스 모드의 운영 UI 지연 기록은 게이트웨이 프로세스만 포함하며 검사기 내부 시간은 제공하지 않습니다. 처리량이나 첫 콘텐츠 지연 개선을 보장하지 않으며 전체 응답 버퍼링은 유지됩니다.

게이트웨이는 지원되는 응답 전체를 수집·검사한 뒤 콘텐츠를 전달합니다. 첫 콘텐츠 지연에는 검사뿐 아니라 응답 수집도 포함됩니다. 완성된 결과를 기다릴 수 있는 작업에 적합하며, 대화형 채팅은 명시적인 지연 예산으로 평가해야 합니다.

## 재현

Docker, Python 3.11 이상과 프로젝트 console 의존성이 필요합니다. 명령은 일회용 스택을 빌드하고 실제 자격증명이나 유료 API 없이 실행하며 finally에서 컨테이너와 볼륨을 제거합니다. 배포 판단 전 유휴 호스트에서 최소 세 번 반복하세요.

```bash
python -m pip install -e ".[console,compat,llm-compat]"
python -m examples.latency.benchmark --output /tmp/latency.json
```

## 해석

운영 UI는 현재 프로세스의 단계별 최근 256개 표본을 표시합니다. 게이트웨이 시간은 클라이언트 전달 전 응답 준비 시점에 끝납니다. Envoy 왕복에는 요청 검사·상류 응답 수집·응답 검사·전송이 포함됩니다. 검사 시간에는 작업자 큐 대기가 포함됩니다. 실패 포함 분포이며 요청별 연결 관계가 없어 서로 뺄 수 없고 재시작 시 초기화됩니다. 표본 없음은 미측정이지 0이 아닙니다.

## 경계

64개 동시 요청에서 32개 완료, 32개 HTTP 503 거절이었으며 불완전한 HTTP 200 SSE는 없었습니다. 분할 이메일 PII는 마스킹됐습니다. 테스트 전용 32 KiB 제한을 넘는 출력은 콘텐츠 토큰 없이 HTTP 500, 10초 상류 시간 초과는 토큰 없이 504를 반환했습니다. 잘못된 자격증명은 401입니다. 상태 코드만으로 실패한 구성요소를 특정할 수 없습니다. 실제 기본값은 다릅니다.

## 0.45 요청별 지연과 동시 처리

운영 UI는 현재 프로세스에서 완료된 최근 64개 게이트웨이 요청의 시간 기록을 보여줍니다. 각 행에는 숫자 시간, HTTP 상태와 완료 여부만 저장합니다. 서명된 임의 ID로 어댑터와 검사 단계를 내부 연결하며 화면에는 내보내지 않습니다. 본문·경로·자격증명·에이전트 신원은 저장하지 않습니다. 초기 인증·진입 거절은 게이트웨이 결과에 표시됩니다.

검사 스트림 대기, 작업자 큐 대기와 실행 시간을 따로 표시합니다. 본문 대기는 응답 메타데이터 검사 후부터 버퍼링된 본문이 검사기에 도착할 때까지입니다. 상류 생성·전송·Envoy 버퍼링을 포함합니다. 구간이 겹치거나 전송 공백이 있으므로 더하거나 모델 순수 지연으로 부르면 안 됩니다. 재시작하면 기록이 초기화됩니다.

`gateway_max_inflight` 설정은 정수 4~64를 허용하고 기본값은 32입니다. 변경은 스테이징 후 유지보수 재시작으로 적용합니다. 연결 마법사는 설정을 유지합니다. 초과 요청은 HTTP 503입니다. 낮은 값은 처리 가능한 요청 수를 줄여도 지연이 중요한 업무에만 적합합니다. 합성 비교에서 48은 버스트 완료 수를 늘리지 못했고 HTTP 500도 발생했습니다.

단일 합성 실행으로 모든 환경의 정답을 정할 수 없습니다. 아래 비교를 재현한 뒤 실제 호스트에서 대표 응답·동시성·제공자 한도·첫 콘텐츠와 완료 지연 예산으로 판단하세요.

### 로컬 합성 비교 (2026-09-22)

설정마다 2회 반복했습니다. 32개 청크의 지연 SSE 픽스처, 본문 한도 32 KiB, 검사 스트림 16개, 검사 작업자 4개를 사용했습니다. 동시성 32에서 회당 64건, 동시성 64에서 회당 128건을 전송했습니다. 첫 콘텐츠 p95 범위는 동시성 32에서 완료된 HTTP 200 응답만 대상으로 합니다.

| 게이트웨이 한도 | 동시성 32 완료 | 첫 콘텐츠 p95 | 동시성 64 완료 | 동시성 64 HTTP 500 | 앱 CPU / 메모리 표본 최대값 |
|---:|---:|---:|---:|---:|---:|

| 16 | 회당 16/64 | 1.53–1.54초 | 회당 16/128 | 0 | 110% / 127 MiB |

8~32에서 HTTP 200이 아닌 시도는 모두 503이었습니다. 성공 응답은 모두 완전했고, 설정별 복구 요청 4건도 모두 성공했습니다. 자원 사용 표본은 짧은 피크를 놓칠 수 있습니다. 48에서 나온 HTTP 500의 원인은 분리 진단하지 않았으므로 Python 병목으로 단정할 수 없습니다. 첫 콘텐츠 지연의 주요 제품상 절충은 전체 응답 버퍼링입니다.
